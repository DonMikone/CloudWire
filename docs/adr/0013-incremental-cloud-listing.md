# Offline syncs list only the Nextcloud folders that changed

A bisync run with nothing to do still lists both sides completely, and with Nextcloud the cloud side is one `PROPFIND Depth:1` per folder (the webdav backend has no fast-list). On the Mac Studio a Files item with 4,589 folders took 85–205 s per run, almost all of it cloud listing (the local walk takes 0.4 s, 1.65 s at background priority), and it ran every ~2 minutes: its ETag check watched the cloud root, which every upload of another Offline Item or the Mount changes. Three changes address this. (1) The remote check of a Files item compares a digest of its Selection entries' ETags (one `PROPFIND Depth:1` per parent folder, `selectionETag`) instead of the root ETag; Nextcloud propagates ETags to every parent folder, so the digest changes exactly when something inside the Selection changes. (2) bisync lists 16 folders in parallel instead of rclone's 8 (`Checkers`, Advanced settings override it); 16 stays gentle on hosted servers. (3) A fork patch gives bisync a listing cache (`--listing-cache off|refresh|use`, `cmd/bisync/listcache.go`): the march records the raw Path2 entries of every folder with the folder's ETag and `oc:fileid` as its parent's listing reported them, and the next run serves a folder from that record when both markers are unchanged, so a run without cloud changes needs one PROPFIND instead of one per folder.

Consequences: the cache is a separate file in the bisync workdir (`*.path2.lsc`); the `.lst` format is untouched. Every run removes it first and only a successful run writes a new one, so any failure, panic, kill, expired lock, `--recover` or `--resync` leads to a full listing. Folders that are mount points (`M` in `oc:permissions`: external storage, shares) or contain one are always listed, because Nextcloud does not reliably propagate their ETags. Requiring the file id as well catches a folder deleted and recreated under the same name. CloudWire sends `refresh` (full listing, renewed cache) at Core start, on the hourly safety run, after a failed run and after a confirmed Mass-Delete Guard stop, and `use` otherwise; other Connections keep `off`. A change the server failed to propagate is therefore seen at the latest by the next safety run. Only the march reads the cache: copies, deletes, conflict checks and recheck work on the real Path2 Fs. Tests: `cmd/bisync/listcache_test.go` (full bisync runs against a local Path2 whose folders report propagating ETags), `backend/webdav` `TestListReportsDirectoryChangeMarkers`, `TestListingCacheModeFollowsSafetyRunsAndFailures`, `TestSelectionETag*`; the integration tests run every scenario with the cache on.

Amendment (docs/adr/0014): a delete on Path1 whose evidence is a Path2 entry missing from a cached folder listing is confirmed by a fresh `PROPFIND` of that folder before it runs, because a stale ETag would otherwise turn into a local deletion; the cache ships only together with ADR 0014.

Considered: `Depth: infinity` PROPFIND as a ListR. Rejected: one huge response per run, discouraged by Nextcloud for large trees, unsupported by other servers, and still a full listing. Considered: skipping bisync entirely when neither FSEvents nor the ETag check saw a change. Rejected: bisync must build its listings each run, and FSEvents history is lost across Core restarts. Considered: reusing the previous `*.path2.lst` as the cache. Rejected: `modifyListing` patches it after the march and rollbacks write old values back, so it is not a record of the server's state. Considered: more parallel listings only (32+). Rejected for hosted servers; the cache removes the requests instead of crowding them.
