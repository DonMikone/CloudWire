# Renames in Offline Items are detected by identity and applied as moves

Before every bisync run the worker compares the synced paths of an Offline Item with a snapshot taken after its last successful run and finds renames and moves by identity: the APFS/HFS+ inode locally (on volumes without persistent inodes, an exact tree match of relative paths, sizes and modification times), the Nextcloud/ownCloud `oc:fileid` or the rclone object ID in the cloud. Each rename becomes one server-side move in the cloud or one local rename, never a deletion plus a new transfer; renames never count for the Mass-Delete Guard. Local wins when both sides renamed the same path differently, a rename wins over a deletion (the content is transferred again under the new name), and a target that already exists on the other side with another identity stops the item without moving anything. Afterwards CloudWire rewrites bisync's listings (including the `-old` backups `--recover` reverts to) and its filters hash, so bisync never sees the rename. A rename or deletion of a synced path during a run stops the run so the next one applies it at once. A renamed or moved Storage Location is followed by its inode; only for items created before 0.3.0, whose root is a cloud folder, a new folder name also renames that cloud folder.

We need this because bisync alone cannot keep a rename: the anchored Selection filters (ADR 0010) hide the new name, so bisync sees only a deletion, and a resync is a union copy that brings the old name back. The cost is a coupling to bisync's listing format v1; integration tests pin it, and an unknown format falls back to a resync.

Considered: rclone's `--track-renames`. Rejected because it is ignored during a resync, needs both names inside the filters and still counts renames toward `--max-delete`. Considered: a resync after every rename. Rejected because it copies everything again and resurrects deletions.
